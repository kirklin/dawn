## 评估方法

每个版本先回答以下问题，再作决定。无需计算一个总分，重点是把收益、证据和投入讲清楚。

| 评估维度 | 需要回答的问题 | 判断记录 |
| --- | --- | --- |
| 用户价值 | 哪一类用户遇到什么具体问题？解决后用户能完成什么过去较难的任务？ | 强 / 中 / 弱：__________ |
| 证据可信度 | 截图反馈、现有行为或访谈是否支持这个问题？哪些判断仍是假设？ | 强 / 中 / 弱：__________ |
| 技术与数据准备度 | 当前代码、数据来源、精度和覆盖是否支撑交付？缺的依赖是什么？ | 已具备 / 可补齐 / 阻塞：__________ |
| 投入与维护 | 实施复杂度、API 调用成本、人工维护和长期运营由谁承担？ | 可接受 / 需缩小 / 不可接受：__________ |
| 结果可验证性 | 上线后观察什么行为或质量指标？什么结果表示继续、调整或停止？ | 指标与门槛：__________ |

**建议决策规则：** 只有用户价值清楚、数据/技术可支撑、验收可观察且维护投入可接受时，直接纳入实施。若价值成立但依赖未满足，选“补条件后评估”，并明确条件。涉及地点安全、虚假精度、数据来源授权或预报误导的风险未解决时，不进入公开发布。

**范围：** 在地点列表增加“本地｜探索”；用首批城市目录浏览候选点；点开单个地点看预报，收藏时再显式加入本地列表。

### 0.4 · 远期趋势

**范围：** 评估并可能扩展当前四天的预报范围；按时效标注趋势与数据可信度；评估支持者功能。

**预期价值：** 帮助用户提前安排周末或出行。

**待确认：** 天气、云层、风场和气溶胶各自覆盖多久？缺失数据怎样影响等级？是否有可持续的额外数据源和成本预算？14 天远期是否足够支持产品表达？
